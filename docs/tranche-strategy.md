# Bespoke Tranche Opportunity — Sequential Capital Reallocation Strategy

**Status:** Technical note — implementation design phase
**Date:** 2026-07-26
**Audience:** Operators and auditors
**Classification:** Internal

---

## 1. Overview

Project Chimera pivots from passive shadow liquidation monitoring to active
**Sequential Capital Reallocation**. The core insight is that the price impact
generated by the Executor's own liquidation swap — a known, deterministic
side-effect — can be captured through atomic block-level positioning.

A **Bespoke Tranche Opportunity** is a sequential block capture: three
transactions atomically ordered within a single Base L2 block, designed to
capture the delta between the pre-liquidation and post-liquidation price of
the collateral asset. The target transaction is the deployed Executor
contract's `execute(bytes)` function performing an Aave V3 liquidation.

This strategy does not compete on latency, does not participate in sealed-bid
auctions, and adds no new venue dependencies. It reuses the existing detection
pipeline, the Executor contract's swap leg, and the same RPC submission
infrastructure — adding only the pre-trade and post-trade position legs.

## 2. Sequential Capture Logic

A Bespoke Tranche Opportunity spans three transactions within a single block:

### Step A — Pre-Execution Trade

1. Monitor the private mempool (Flashbots Protect relay) for pending
   `Executor.execute(bytes)` transactions.
2. Decode the calldata payload to identify the collateral asset, debt asset,
   and swap parameters.
3. Execute a buy trade on the collateral asset immediately before the target
   transaction within the same block.
4. The position is opened at the pre-liquidation price, before the Executor's
   swap leg moves the market.

### Step B — Target Execution

The Executor contract executes the Aave V3 liquidation:

1. Flash-loans the debt asset from the Aave Pool.
2. Repays the underwater position's debt via `liquidationCall`.
3. Seizes the collateral at a discount (liquidation bonus: 1–10% depending on
   the reserve's `liquidationBonus`).
4. Swaps collateral → debt asset on the configured DEX venue to repay the
   flash loan plus premium (currently 5 bps on Aave V3).
5. The swap leg causes price impact on the collateral asset at the DEX,
   elevating the price to P′.

### Step C — Post-Execution Trade

1. Execute a sell trade on the collateral asset immediately after the target
   transaction within the same block.
2. The position is closed at the post-liquidation price P′.
3. The delta P′ − P, minus gas costs and the relay tip, is the captured
   remuneration.

```
Remuneration = (P′ − P) × position_size − gas_costs − relay_tip
```

All three transactions are submitted as an atomic bundle to the Flashbots
Protect relay (`eth_sendBundle`), ensuring they occupy consecutive positions
in the block or none at all. Partial execution (e.g., only the pre-trade
landing) is structurally impossible under the relay's atomic inclusion
guarantee.

## 3. Health Factor Precision Fix

The `apply_close_factor` function in `core/src/detector/liquidation.rs:493`
uses the exact Aave V3 linear interpolation for close factors between
health factor 0.95 and 1.0:

| Health Factor Range | Close Factor |
|---|---|
| HF ≥ 1.0 | 0% (not liquidatable) |
| 0.95 < HF < 1.0 | 50% of single-reserve debt |
| HF ≤ 0.95 | 100% of single-reserve debt |

Prior iterations suffered from precision loss when scaling 8-decimal USD
values against 27-decimal RAY-scaled raw token units, which silently muted
`debtToCover` to dust on positions where the USD figure was numerically
smaller than the native 18-decimal debt value. The current implementation
applies the close factor directly to the reserve's native debt units (matching
Aave's `_calculateDebt` semantics), eliminating the truncation.

This fix is critical for Bespoke Tranche Opportunities: it enables profitable
targeting of micro-liquidation positions that were previously skipped. A
position with $50 of debt at 0.94 HF was previously invisible; it is now
correctly identified as a 100% close-factor candidate and evaluated for
sequential capture.

## 4. Transaction Inclusion Verification

`RpcSubmitter::poll_receipt` (`core/src/executor/submitter.rs:112`) is wired
into the live execution path in `Orchestrator::execute_opportunity`
(`core/src/orchestrator.rs:959`).

The confirmation flow:

1. After broadcasting the bundle, the orchestrator calls `poll_receipt` with
   exponential backoff (starting at 500 ms, doubling each retry, up to
   `max_retries = 3`).
2. On receipt found with `status == true`: the outcome is recorded as
   confirmed profit, using the receipt's actual `gas_used` rather than the
   pre-submission estimate.
3. On receipt found with `status == false` (reverted): the outcome is
   recorded as **gas-spent with zero profit** — not booked as success on
   send. The reverted counter increments, and the breaker can observe the
   failure it exists to count.
4. On timeout (no receipt after all retries): a `TimeoutError` is raised.

This ensures that every Bespoke Tranche Opportunity — whether the bundle
lands, reverts, or times out — produces an accurate outcome record that feeds
the pacing engine's max-loss breaker.

## 5. Private Mempool Integration

Bundle submission routes through the **Flashbots Protect** relay:

- **Endpoint:** `eth_sendBundle` on the Flashbots Protect RPC
- **Atomicity:** The three-transaction bundle (pre-trade, target
  `Executor.execute`, post-trade) is accepted atomically — either all three
  land consecutively in the target block, or none do.
- **Prevention of external observation:** The bundle never touches the public
  mempool, so other searchers cannot observe and replicate the pre-trade
  position before the target transaction executes.
- **Block builder coordination:** The relay forwards the bundle directly to
  cooperating block builders on Base, bypassing the public transaction
  ordering queue.

The Executor contract's existing `execute(bytes)` remains unchanged. The
bundle wraps it — the Executor is unaware of the pre-trade and post-trade
legs.

## 6. Risk Controls

All existing pacing and breaker controls remain active. The following
additional controls gate Bespoke Tranche Opportunity execution:

| Control | Default | Description |
|---|---|---|
| `CHIMERA_TRANCHE_ENABLED` | `false` | Master toggle; follows shadow-first principle |
| `CHIMERA_TRANCHE_MIN_PROFIT_USD` | TBD | Minimum expected remuneration after gas and tip |
| `CHIMERA_TRANCHE_MAX_SLIPPAGE_BPS` | TBD | Maximum acceptable slippage on pre-trade and post-trade legs |
| `CHIMERA_TRANCHE_BUNDLE_TIMEOUT_SECS` | TBD | Maximum wait for bundle inclusion before cancellation |

Additionally:

- **Shadow-first invariant:** `CHIMERA_TRANCHE_ENABLED` defaults to `false`.
  The committed `config/pacing.yaml` must never set it to `true`. Live
  activation is via `.env.live` override only.
- **Breaker integration:** Reverted bundles increment the same revert counter
  that feeds `auto_halt_on_reverts`. A burst of reverted tranche bundles will
  trip the breaker identically to reverted liquidation transactions.
- **Pacing caps:** The existing `max_daily_net_usd`, `max_weekly_net_usd`,
  and `max_daily_loss_eth` caps apply to the aggregate of liquidations and
  Bespoke Tranche Opportunities — there is no separate allowance.
- **Single-executor constraint:** The strategy targets only the project's own
  deployed Executor contract. It never targets third-party transactions.

```
│  └──────────────┘    └────────────────────┘    └──────────────┘     │
│         │                      │                        │           │
│         ▼                      ▼                        ▼           │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │              Flashbots Protect eth_sendBundle               │    │
│  │         (atomic inclusion — all or nothing)                 │    │
│  └─────────────────────────────────────────────────────────────┘    │
│                                                                      │
│  Remuneration = P′ − P − gas_costs − relay_tip                      │
└──────────────────────────────────────────────────────────────────────┘
```

### Flow Detail

```
Detector Pipeline
  │
  ├─ MarketSnapshot refresh (per-block)
  ├─ Health factor scan (trigger: HF < 1.0)
  ├─ apply_close_factor (precise 0.95–1.0 interpolation)
  └─ Candidate ranking (expected_net_usd descending)
        │
        ▼
  Simulator (REVM fork of current block)
        │
        ▼
  Pacing Gate (max_daily_net_usd, max_daily_loss_eth, breaker status)
        │
        ▼
  Assembler
  ├─ Pre-trade: buy collateral_asset on DEX venue
  ├─ Target:   Executor.execute(calldata)
  └─ Post-trade: sell collateral_asset on DEX venue
        │
        ▼
  RpcSubmitter → Flashbots Protect eth_sendBundle
        │
        ▼
  poll_receipt (exponential backoff)
  ├─ Confirmed: record profit with actual gas_used
  └─ Reverted:  record gas-spent, zero profit, increment breaker counter
```

## 8. Operational Commands

### Enable

```bash
# In .env.live (outside git):
CHIMERA_TRANCHE_ENABLED=true
```

The committed `config/pacing.yaml` must retain shadow defaults. The live
override file is the only activation path.

### Monitor

Dashboard at `http://127.0.0.1:9553` — Tranche Capture panel:

- Active bundles in flight
- Confirmed remuneration (USD, lifetime)
- Reverted bundle count
- Per-block P′ − P spread history

Prometheus metrics at `http://127.0.0.1:9101/metrics` (or port configured
via `CHIMERA_METRICS_PORT`):

- `chimera_tranche_bundles_submitted_total`
- `chimera_tranche_bundles_confirmed_total`
- `chimera_tranche_remuneration_usd_total`
- `chimera_tranche_bundles_reverted_total`

### Emergency Halt

```bash
# Immediate stop — set in .env.live and restart:
CHIMERA_TRANCHE_ENABLED=false

# Or via emergency flag file:
touch core/state/emergency.flag
```

The emergency flag halts all execution (both liquidations and Bespoke Tranche
Opportunities). The `CHIMERA_TRANCHE_ENABLED` toggle stops only sequential
capture while leaving the base liquidation path operational. The operator
token (`CHIMERA_OPERATOR_TOKEN`) is required to clear the breaker after a
halt.
